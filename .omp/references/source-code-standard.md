## 目标与优先级

保持人工源码格式稳定、差异清晰并具备注释主导的分层可理解性。阅读者仅阅读注释、代码结构和少量高价值代码，就应能够理解代码是什么、如何工作以及为什么这样设计，而无需依赖原始对话或作者记忆。

按以下优先级确定具体格式：

1. 用户对本次任务的明确要求；
2. 仓库内已生效的 formatter、linter、`.editorconfig` 或团队规范；
3. 当前文件中占主导且一致的既有风格；
4. 本规范提供的默认规则。

不得为了套用默认规则覆盖项目已经明确配置的风格。不得把局部实现或修复扩大成无关文件、无关模块或全仓库格式化。

## 适用范围

本规范只管理源码格式、导入、注释和验证等源码表达要求。Java 代码的业务领域、职责分层、对象边界、依赖方向及相关工程约定由 `.omp/references/java-domain-architecture-standard.md` 管理；两份规范并列适用，不在此重复维护。

- `[I]` 修改人工编写的生产或测试源码时，编辑前完整读取本规范，并按本规范审核任务涉及的每个变更源码文件。
- `[F]` 修改人工编写的生产或测试源码时，编辑前完整读取本规范，在缺陷修复范围内保持格式与注释准确，不借机进行无关整理。
- 文档、配置、依赖元数据或纯生成代码任务无需加载本规范；同时包含人工源码时，仅对人工源码应用。
- 不主动修改第三方、vendor、压缩或自动生成源码。必须修改生成代码时，先确认事实源和再生成策略，并在结果中说明风险。

## 通用代码格式

### 缩进与空白

- 使用空格缩进；项目明确要求 Tab 时遵循项目配置。
- 每个嵌套层级只增加一级缩进，不使用空格把续行垂直对齐到任意标识符或左括号。
- 删除行尾空格；文件末尾保留且只保留一个换行。
- 使用一个空行分隔职责不同的代码块、方法或导入组；不使用连续多个空行制造视觉层级。
- 逗号、分号或其他行末标点后不得保留无意义空格。

### 行宽与换行

- 项目没有明确限制时，以 120 个字符为默认行宽上限。
- 简短、语义完整且不超过行宽的声明、调用和表达式保持单行。
- 发生换行时按语义边界拆分；同一参数列表、集合项或配置项采用一种排列方式，不混用悬挂对齐和固定缩进。
- 不通过缩写业务名称、压缩空格或牺牲可读性强行满足行宽。

### 括号与代码块

- 同一文件使用一致的大括号风格；无项目规范时，开始大括号放在声明或控制语句同一行。
- 结束大括号与对应声明或控制语句的起始缩进对齐。
- 即使语言允许，也不为了少一行而压缩包含实质逻辑的代码块。

### 变更边界

- 优先只格式化本次实际修改的文件和必要相邻范围。
- 用户明确要求统一整个文件，或文件内部格式混乱会持续干扰修改时，可以统一整个文件并在结果中说明。
- 格式化不得改变控制流、调用顺序、数值、字符串、序列化结构或公共契约。

## Java 格式

### 基础缩进

- Java 默认使用 4 个空格作为一个缩进层级，不使用 Tab。
- 类成员相对类声明缩进 4 空格；方法体相对方法声明再缩进 4 空格。

### 多行参数与调用

方法声明需要换行时，左括号保留在方法名后，每个参数独占一行并相对声明增加 4 空格，右括号回到声明起始层级：

```java
public Result calculate(
    Input input,
    MonitorContext context
) {
    // ...
}
```

构造器、方法调用和注解参数需要换行时使用相同规则：

```java
return new Result(
    input,
    context,
    System.currentTimeMillis()
);
```

```java
@ConditionalOnProperty(
    prefix = "fusion.monitor.trace",
    name = "enabled",
    havingValue = "true",
    matchIfMissing = true
)
```

- 多行参数或实参一行一个，逗号紧跟当前项，逗号后不保留行尾空格。
- 不把第一项留在左括号后、其余项另起行。
- 不按第一个参数的字符位置做大段空格对齐。
- 单参数或能清晰放入一行的短调用保持单行。

### 类与方法间距

- package、各 import 组、顶层类型之间各保留一个空行。
- 相邻方法之间保留一个空行。
- 文档注释紧邻其描述的类、字段、构造器或方法，中间不插入空行。

## 导入规范

- 只保留实际使用的 import；删除未使用和重复 import。
- 默认使用显式类型 import，不使用 `*` 通配符；项目生成器或既有强制规范明确要求时除外。
- 按顶级包分组，组名按字母顺序排列；每组之间保留一个空行。
- 组内按完整限定名逐字符升序排列，不按类名或添加时间排序。
- 静态导入与普通导入分组分开，并在自身组内按完整限定名排序。
- 不为减少 import 数量而在正文中反复书写全限定类名；名称冲突需要消歧时除外。

示例：

```java
import com.fasterxml.jackson.databind.ObjectMapper;
import com.quansheng.monitor.service.runtime.MonitoringService;
import com.quansheng.monitor.service.trace.TraceLedger;

import java.util.List;

import javax.sql.DataSource;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
```

## `[I]` 注释要求

### 总体目标

将注释作为实现的主要阅读入口，将类与方法签名、核心调用、关键条件、重要数据转换、状态变化和最终返回作为注释的事实验证。所有新增或修改的注释使用中文；项目明确规定其他语言时遵循项目规则。

对 `[I]` 任务涉及的每个变更源码文件，审核文件内全部人工编写的代码对象、方法、函数和构造方法，而不只审核本次直接修改的行。

### “是什么”：代码对象与方法

为每个变更源码文件中的类、接口、枚举、记录类型、模块级对象及相近层级代码对象添加块级文档注释，说明：

- 它在系统或业务中的职责；
- 它代表、管理或协调的对象；
- 必要时说明它与主要协作者的边界。

不要只把名称拆成自然语言，也不要在对象注释中复述所有字段。

为每个变更源码文件中的方法、函数和构造方法添加块级文档注释。对包含实质逻辑的匿名函数、回调或相近可执行单元，在定义前说明其职责。

方法注释至少说明方法是什么以及完成什么职责；存在前置条件、重要副作用、异常语义或调用顺序约束时一并说明。

参数和返回说明遵循以下要求：

- 方法包含两个或更多参数时，使用语言对应的 `@param`、`:param` 或 XML 参数标签逐项说明全部参数；
- 单参数的含义、单位、范围、来源或可空性不明显时，也说明该参数；
- 返回值不是 `void`、`None` 或等价空返回，且属于对象、集合、结果包装或其他非基础类型时，使用语言对应的 `@return`、`:return` 或 XML 返回标签说明结果内容和语义；
- 标签说明业务含义和约束，不只重复参数名或类型名。

### “怎么做”：方法内部流程

在方法内部按逻辑阶段添加行级注释，使这些注释按顺序阅读时能够串联出方法的主要执行流程。

常见阶段包括输入校验、数据准备、查询、过滤、转换、核心计算、持久化、事件发布、结果组装和资源清理。阶段以实际职责划分，不按固定行数机械切块。

满足下列任一情况时，通常应开始一个带注释的逻辑阶段：

- 一组语句共同完成一个可命名的子目标；
- 数据从一种业务状态或表示转换到另一种；
- 执行从准备阶段进入核心处理、持久化或输出阶段；
- 较长方法中的下一段代码需要重新建立阅读上下文。

在复杂方法或重要组件调用前添加行级注释，说明该调用在当前流程中承担的阶段职责。以下调用通常视为复杂或重要调用：

- 跨模块、跨层、远程服务、仓储、消息、事务或外部系统调用；
- 算法、批量处理、坐标或格式转换、序列化、解析和聚合调用；
- 涉及并发、异步、安全、缓存、重试、补偿或资源生命周期的调用；
- 方法名无法让不了解上下文的阅读者直接判断其业务作用的调用。

不要为简单 getter、普通集合访问、显然的工具方法或已被紧邻阶段注释充分覆盖的调用重复添加低价值注释。

### “为什么”：业务与流程决策

在由业务规则、流程状态或非显然技术约束产生的判断和分支前添加行级注释，说明分支为什么存在以及保护什么行为。重点覆盖：

- 业务准入、排除、优先级和状态转换规则；
- 提前返回、跳过、降级、兜底、补偿和重试条件；
- `if`、`switch`、模式匹配、异常分支或循环终止中承载的流程规则；
- 兼容性、性能、并发、安全、历史数据或外部系统限制；
- 看似可以删除、合并或改序，但实际受约束的逻辑。

解释规则来源或设计原因，不要只把条件表达式翻译成中文。

低价值示例：

```java
// 判断任务是否结束
if (task.isFinished()) {
```

高价值示例：

```java
// 业务规定已结束的飞行任务不能再次参与实时轨迹融合
if (task.isFinished()) {
```

普通语法控制、显然的空值防御或没有额外业务与流程含义的简单分支，不要求机械添加“进入循环”“判断是否为空”等注释；其目的或影响需要推理时必须说明。

### 注释质量

注释必须满足：

- **准确**：与最终代码、边界和顺序一致，修改逻辑时同步修改；
- **就近**：放在对应对象、阶段、复杂调用或决策之前；
- **连续**：方法内阶段注释能够形成完整且顺序正确的流程骨架；
- **具体**：使用业务和系统概念，避免“处理数据”“调用方法”等空泛表述；
- **解释性**：补充代码无法直接表达的职责、流程和原因，不逐行复述语法；
- **适量**：覆盖所有需要理解的部分，同时避免重复同一事实；
- **可维护**：不记录临时讨论、过期计划、作者心理过程或容易与代码失真的细节。

优先通过清晰命名和合理拆分降低理解成本，再用注释保存无法仅靠代码表达的结构、流程和决策语义。不要用长注释掩盖职责混乱的方法。

## `[F]` 注释要求

- 修复改变职责、流程、条件、顺序、单位、边界或异常语义时，同步修正相关文档注释和行级注释。
- 新增类或方法时，遵循 `[I]` 的对象与方法注释要求。
- 新增复杂流程、关键调用或非显然决策时，遵循 `[I]` 的“怎么做”和“为什么”要求。
- 不因小范围修复强制补写整个历史文件的所有缺失注释；除非缺失注释会妨碍理解或导致修复后的代码与说明矛盾。
- 不保留描述旧缺陷、旧条件或旧处理顺序的失真注释。

## 语言适配

使用目标语言和项目既有风格支持的文档注释形式：

- Java、Kotlin：Javadoc/KDoc；
- TypeScript、JavaScript：TSDoc/JSDoc；
- Python：Docstring；
- C#：XML documentation comments；
- Go：紧邻声明、以对象名称开头的文档注释；
- 其他语言：使用其标准文档注释与普通行注释形式。

语言不支持 `@param` 或 `@return` 时，使用该语言等价的结构化说明。不要为了标签形式破坏目标语言的标准风格。

## 审核与验证清单

### 格式

1. 是否遵循用户要求、项目 formatter/linter 和当前文件主导风格？
2. 缩进、续行、括号和空行是否一致？
3. 是否存在 Tab 混用、行尾空格、重复空行或超过默认行宽的可避免长行？
4. import 是否实际使用、显式、分组正确并按完整限定名排序？
5. 是否避免格式化无关代码和改变程序语义？

### `[I]` 注释

1. 每个变更源码文件中的所有类及相近层级对象是否都有说明“是什么”的块级注释？
2. 每个方法、函数和构造方法是否都有块级注释？
3. 多参数方法是否逐项说明全部参数，必要的单参数说明是否完整？
4. 非空、非基础类型返回是否有结构化返回说明？
5. 方法内部阶段注释能否按顺序串联出“怎么做”？
6. 每个复杂或重要调用前是否说明其当前流程职责？
7. 业务、流程和非显然技术分支是否解释了“为什么”？
8. 是否存在只复述名称、类型、条件或语法的低价值注释？
9. 注释是否与最终代码一致，没有因实现调整而过期？
10. 隐去普通实现语句后，阅读者能否根据注释、结构和少量高价值代码正确复述代码？

### `[F]` 注释

1. 修复是否使既有注释失真？
2. 新增对象、方法、复杂流程和关键决策是否具备必要说明？
3. 是否在保持修复最小化的同时，消除了与缺陷直接相关的注释债务？

### 验证

- 运行项目已有 formatter 或 lint 检查；没有对应工具时至少执行差异格式检查。
- 按风险运行编译、测试、类型检查或目标场景验证。
- 在结果中说明格式与注释审核、实际验证以及剩余风险。
