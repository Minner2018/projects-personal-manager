## 定位与适用范围

本规范是仓库内 Java 服务端项目的默认领域架构与工程规范，主要回答以下问题：

- 新增代码属于哪个业务领域和职责层；
- 对象应当表达哪一侧的契约，由谁拥有；
- 各层、各领域和基础设施之间可以如何依赖；
- 日志、配置、异常、数据访问和事务边界应当如何设计；
- 在不破坏已有项目一致性的前提下，如何让新代码逐步收敛。

本规范与 `.omp/references/source-code-standard.md` 并列适用。源码格式规范管理缩进、换行、导入和注释等源码表达；本规范管理代码职责、位置、依赖和工程边界。两份规范不得相互替代。

本规范适用于人工编写的 Java 生产和测试源码，以及与其直接配套的应用配置、日志配置、Mapper XML 和基础设施资源文件。非 Java 项目可以参考其中的架构原则，但不得机械套用 Java 包结构、类型后缀或框架约定。

本规范是默认值，不要求为了形式完整而创建空包、空接口、空实现或无实际规则的领域对象，也不要求把单体工程拆成多个构建模块、把每张表设计成聚合根，或用类型和设计模式的数量衡量领域建模程度。

## 规则优先级与既有项目适配

按以下优先级确定实际做法：

1. 用户对本次任务的明确要求；
2. 目标项目已生效的架构文档、团队规范、构建约束、框架配置和自动检查；
3. 目标项目或当前模块中稳定、占主导的既有实现方式；
4. 本规范提供的默认规则。

只有在默认规则与已有项目的明确约定或稳定实现发生冲突时，才按已有项目的做法处理。判断“项目既有风格”时，应优先寻找以下证据：

- 项目内明确记录的规则或架构决定；
- 构建、框架、代码生成器或静态检查形成的真实约束；
- 相关模块多个代表性文件中重复出现且语义一致的做法；
- 维护现有公共契约、序列化结构、数据库映射或运行机制所必需的兼容行为。

单个文件、单处历史遗留、已被其他证据否定的写法或明显偶发的不一致，不足以代表项目风格。项目内部同时存在多种做法时，优先采用当前模块占主导且与任务最接近的模式；仍无法判断时使用本规范默认值，并说明关键假设。

应用本规范时遵守以下边界：

- 不为了符合默认目录或分层而扩大当前任务范围；
- 不借功能开发或局部修复批量迁移历史代码；
- 新代码优先与所在项目保持一致，再在没有既有约定的部分使用默认规则；
- 需要改变项目既有架构或长期约定时，将其作为明确的重构或架构决策处理；
- 发现历史偏差时可以保留兼容，但不得把偏差扩散到无关的新模块。

## 架构目标与基本原则

### 按业务能力纵向组织

先判断代码属于哪个业务领域，再判断它属于领域内部的哪一层。不得用 `controller`、`service`、`dao` 等技术类型作为整个项目的顶层业务分类。

### 依赖面向业务核心

默认依赖方向为：

```text
interfaces -> application -> domain
infrastructure -> application/domain 中定义的端口
```

`domain` 不依赖 Web、数据库、缓存、消息、网络协议或具体框架实现。`infrastructure` 提供技术能力并实现内层定义的端口，不得反向决定领域模型。

### 简单优先

只为当前业务复杂度引入必要的实体、值对象、领域服务、事件和端口。简单查询或配置维护不必强行复制完整的领域对象、持久化对象和转换器体系，但简化不能破坏已有明确边界。

### 领域归属优先于复用

少量代码重复不等于应当进入公共模块。先确认代码是否代表同一个稳定概念、是否有明确所有者，再判断是否共享。

### 渐进演进

历史代码以保持可运行和可交付为前提。新功能遵循当前项目约定和本规范默认值；架构迁移应有独立范围、验证方案和回退考虑。

### 技术细节与敏感信息隔离

协议、数据库、缓存和第三方接口等技术细节不得无边界渗入核心业务。环境差异使用配置机制表达，密码、令牌和密钥不得明文提交。

## 业务领域与模块边界

顶层包或模块默认表达稳定的业务能力边界，名称使用小写业务英文，不使用页面名称、临时需求名称或笼统技术词作为领域名称。

划分领域时综合考虑：

- 是否具有相对独立的业务语言、规则和生命周期；
- 是否有清晰的数据和行为所有权；
- 是否能通过稳定契约与其他领域协作；
- 是否需要独立演进，而不是仅为一次需求临时分类。

不得因为需求名称不同就重复创建领域，也不得把互不相关的业务统一塞入 `operations`、`common`、`shared` 或 `misc`。新增或调整重要领域边界时，应由项目负责人确认；长期影响较大的决定应记录原因和约束。

## 领域内部四层职责

当项目没有其他稳定分层时，每个业务领域默认采用 `interfaces`、`application`、`domain`、`infrastructure` 四层。目录表达职责边界，不是给原有 `controller/service/dao` 机械增加前缀。

### `interfaces`：外部适配层

负责接收外部输入并返回适合对应协议的结果，包括：

- HTTP、WebSocket、SSE、消息监听和其他入口；
- 请求解析、参数格式校验和身份信息提取；
- Request 到 Command/Query 的转换；
- 应用结果到 Response 或协议消息的转换。

默认只与 `application` 交互。Controller 或监听器不得直接访问 Mapper，不开启事务，不编排多个基础设施组件，也不得把 Servlet、网络 Channel 等框架对象传入领域层。

### `application`：应用层

负责表达和编排明确用例，包括：

- 权限校验后的业务流程编排；
- 调用领域对象、领域服务和端口；
- 定义事务边界；
- 处理 Command、Query 和多个入口复用的应用 DTO；
- 协调跨领域调用和外部能力。

应用层不直接实现 SQL、Redis Key、设备协议或第三方报文等技术细节。一个公开方法通常对应一个可以清晰命名的用例。

### `domain`：领域层

负责表达核心业务概念和规则，包括：

- 具有业务身份和生命周期的实体；
- 按属性值判断相等并尽量保持不可变的值对象；
- 维护聚合内部一致性的聚合根；
- 无法自然归属单个实体的核心领域服务；
- 已发生的业务事实形成的领域事件；
- 由业务需要定义的 Repository、Gateway 或其他端口。

领域对象应通过有业务含义的方法维护状态，不默认退化为只含 getter/setter 的数据容器。领域仓储接口描述业务需要的持久化能力，不暴露 SQL、MyBatis、JDBC 或数据库表结构。

### `infrastructure`：基础设施层

负责实现具体技术能力，包括：

- 数据库访问、Mapper、PO 和仓储实现；
- Redis 等缓存实现；
- TCP、Netty、消息中间件和设备协议适配；
- 第三方 HTTP 或 SDK 客户端；
- Spring 及其他框架配置；
- application/domain 所定义端口的实现。

协议报文、数据库 PO、第三方 DTO 和框架回调对象不得直接充当领域对象。技术异常和外部数据应在适配边界转换为上层能够理解的语义。

## 默认目录结构

项目没有既有结构时，可以下列目录作为起点。只创建当前真实需要的目录：

```text
<base-package>.<domain>
├─ interfaces
│  ├─ rest
│  │  ├─ controller
│  │  ├─ request
│  │  └─ response
│  ├─ websocket
│  └─ event
├─ application
│  ├─ service
│  ├─ command
│  ├─ query
│  └─ dto
├─ domain
│  ├─ model
│  │  ├─ aggregate
│  │  ├─ entity
│  │  └─ valueobject
│  ├─ service
│  ├─ event
│  └─ repository
└─ infrastructure
   ├─ persistence
   │  ├─ mapper
   │  ├─ po
   │  ├─ repository
   │  └─ converter
   ├─ cache
   ├─ gateway
   ├─ integration
   └─ configuration
```

包名全部小写并表达明确职责。避免使用 `biz`、`manager`、`handler`、`common`、`base`、`misc` 等含义不清的包承载业务；只有框架或协议已有明确术语时使用对应名称，例如 Netty `ChannelHandler`。

接口与实现类不要求形式化成对存在。只有确有多个实现、替换边界、隔离需求或项目稳定惯例时，才建立接口和 `Impl` 实现。

## 对象类型、命名与转换

对象按所有者和使用边界命名，不按字段相似度统一叫作 DTO 或 VO。

| 类型 | 默认用途 | 默认位置 | 命名示例 |
| --- | --- | --- | --- |
| Request | 外部请求输入 | `interfaces/.../request` | `CreateDeviceRequest` |
| Response | 外部响应视图 | `interfaces/.../response` | `DeviceDetailResponse` |
| Command | 写用例输入 | `application/command` | `RegisterDeviceCommand` |
| Query | 查询用例输入 | `application/query` | `DeviceStatusQuery` |
| Application DTO | 多入口复用的应用数据 | `application/dto` | `DeviceSummaryDTO` |
| Entity | 有业务身份和生命周期的对象 | `domain/model/entity` | `Device` |
| Value Object | 不可变业务值 | `domain/model/valueobject` | `DeviceCode` |
| Domain Event | 已发生的业务事实 | `domain/event` | `DeviceRegisteredEvent` |
| Repository | 聚合持久化端口 | `domain/repository` | `DeviceRepository` |
| PO | 数据库持久化对象 | `infrastructure/persistence/po` | `DevicePO` |
| External DTO | 第三方或设备协议对象 | 对应 `infrastructure` 适配器 | `VendorDeviceDTO` |

新代码不使用含义不清的 `vo` 包：外部返回对象使用 `response`，领域值对象使用 `valueobject`。项目已经对 VO、DO 等缩写形成稳定且无歧义的约定时，遵循项目约定。

默认命名规则如下：

- Controller 使用 `<Resource>Controller`；
- 应用服务使用能表达用例的 `<UseCase>Service`；
- Command 使用“动词 + 名词 + Command”；
- Query 使用“业务名词 + Query”；
- Repository 使用“聚合名 + Repository”；
- Mapper 使用“持久化对象或资源名 + Mapper”；
- 领域事件使用已发生事实的过去式语义并以 `Event` 结尾；
- 配置类使用“职责 + Configuration”。

对象转换遵循边界所有权：

- `interfaces` 负责 Request 到 Command/Query，以及应用结果到 Response 的转换；
- Repository 实现负责 PO 与领域模型之间的转换；
- 第三方或协议适配器负责 External DTO 与应用/领域对象之间的转换；
- 复杂转换放入职责明确的 `converter` 或 `assembler`；
- 不把 Bean 属性批量复制作为默认转换方案，避免隐藏语义差异。

不得直接把领域实体作为 Controller 返回值，也不得把 Request 直接传给 Mapper。跨边界只返回调用方需要的最小结果，不暴露领域内部结构。

## 共享代码

共享模块是受控的共享内核，不是无法归类代码的收容区。代码进入共享模块前，应同时确认：

- 无明确的单一领域所有者；
- 被多个领域以相同语义使用；
- 概念和契约长期稳定；
- 共享带来的耦合小于重复或适配成本。

通常可以共享：

- 统一响应、全局异常转换和全局安全过滤器；
- 日期、编码、哈希等不包含业务规则的纯工具；
- 多领域共同认可且稳定的平台级身份、租户等概念；
- 全局框架、序列化、线程池、缓存、监控和日志配置。

通常不得共享：

- 只服务一个领域的业务类、枚举、常量和校验规则；
- 仅为消除少量重复而抽出的不稳定工具；
- 含具体领域判断的 `CommonUtil`；
- 字段相似但语义不同的第三方 DTO；
- 无法说明负责人和稳定边界的大型 `common`、`base` 或 `misc` 包。

优先由概念拥有者通过稳定的应用接口提供能力，而不是让多个领域共同依赖其内部对象。

## 日志与配置

### 日志

- 使用参数化日志，不通过字符串拼接构造普通日志消息；
- 关键业务日志包含足以定位问题的业务标识和追踪标识；
- 同一异常只在最合适的处理边界完整记录一次，避免多层重复打印堆栈；
- 不记录密码、令牌、密钥、完整授权凭据和未脱敏敏感信息；
- 高频设备数据、原始报文或逐帧信息不使用 `INFO`，详细输出应支持级别、采样、截断或开关；
- 日志描述稳定的事件和结果，避免只有“进入方法”“执行成功”等无法定位上下文的内容。

默认级别语义：

- `ERROR`：业务无法完成或系统异常，需要告警或人工处理；
- `WARN`：可恢复异常、降级、非法状态或需要关注的重试；
- `INFO`：关键业务状态变化和生命周期事件；
- `DEBUG`：开发排查需要的流程、条件和中间信息；
- `TRACE`：高频、逐条或逐帧细节，生产环境默认关闭。

日志框架配置放在项目标准资源位置。日志技术组件可以共享，但业务日志仍由对应领域类记录，不建立集中式日志服务代替正常日志调用。

### 配置

- 配置使用稳定且有所有权的前缀；
- 多个相关配置项优先绑定为类型安全的配置对象，避免大量散落的单值注入；
- 共同配置与环境差异分离，避免在多个环境文件中重复维护相同值；
- 密码、密钥和外部凭据通过环境变量或项目认可的安全配置机制注入；
- 新增配置说明用途、默认值、单位、合法范围和生产安全边界；
- 全局配置放共享基础设施位置，领域专属配置留在对应领域的基础设施层。

配置文件名称、格式和目录以目标项目已有框架约定为准。

## 异常、数据访问与事务

### 异常处理

- 参数格式校验在接口边界完成，并转换为统一外部响应；
- 业务规则不满足时使用含义明确的业务或领域异常，不用 `null` 表示失败；
- 基础设施异常转换为上层能够理解的异常，不向 Controller 暴露数据库或协议实现异常；
- 全局异常处理只负责协议状态和响应转换，不承载业务判断；
- 禁止捕获宽泛异常后仅记录日志并继续执行；确需降级时明确结果、补偿和可观测行为。

### 数据访问

- Mapper、数据库映射对象和仓储实现默认位于基础设施层；
- 核心聚合通过领域仓储端口表达持久化需求；
- SQL 明确列出业务所需字段，避免核心查询长期依赖 `SELECT *`；
- 分页、批量和历史查询评估索引、排序稳定性、超时和最大结果集；
- 领域实体默认不携带 MyBatis 等持久化框架注解；简单 CRUD 一对一映射可以按项目惯例作为明确简化；
- 简单配置表或只读查询可以按项目稳定做法直接使用 Mapper，但不得由此让核心业务绕过领域边界。

### 事务边界

- 事务原则上位于应用服务的公开用例方法；
- Controller、Mapper、事件数据对象和纯领域对象不负责开启事务；
- 事务内避免长时间网络、设备或第三方调用；必要时先持久化状态，再通过事件或任务执行外部操作；
- 数据库、设备和第三方系统之间不存在天然原子事务，应设计幂等、状态机、重试、超时和补偿；
- 事务传播、隔离级别和回滚条件遵循目标项目的数据库与框架约束，不机械使用默认注解参数。

## 跨领域协作

领域之间不得直接访问对方的 Mapper、PO 或内部实现类。默认通过以下方式协作：

- 被调用领域公开的 application service 或稳定端口；
- 表达已发生业务事实的领域事件；
- 明确属于技术连接、协议或消息接收的基础设施事件。

同步调用只返回调用方需要的最小结果。出现循环依赖时，重新检查领域边界，或由更高层的应用服务协调，不通过互相注入内部实现解决。

异步事件应考虑重复消费、顺序、失败重试、超时和服务重启后的恢复。关键业务不能只依赖进程内事件保证可靠性；根据项目基础设施选择事务消息、Outbox、持久化任务或其他可靠机制。

事件命名表达已发生事实，事件体保持稳定且只包含订阅者需要的信息。外部系统契约变化时，在基础设施适配器内隔离变化，不让第三方模型直接扩散到领域内部。

## 开发与渐进演进

新增功能时，默认按以下顺序判断和落位：

1. 确认它属于现有哪个业务领域，是否真的需要新建领域；
2. 定义外部请求和响应契约；
3. 定义能够清晰表达用例的 Command/Query 和应用服务；
4. 把核心状态与规则放入合适的实体、值对象或领域服务；
5. 为必要的持久化和外部能力定义端口；
6. 在基础设施层实现数据库、缓存、协议和第三方适配；
7. 为领域规则、数据映射、接口契约和重要失败路径补充相应测试；
8. 按本规范和项目既有要求执行审核与验证。

处理已有项目时：

- 先检查任务相关目录、代表性实现和显式配置，不要求为局部任务调查整个仓库；
- 默认保留能够稳定运行的已有结构，避免只移动包而不处理运行时引用；
- 新代码与历史结构暂时并存时，明确转换边界，不建立双向随意依赖；
- 包或类型迁移同步检查 import、反射类名、Mapper XML、组件扫描、序列化类型、服务发现和框架扩展文件；
- 需要系统性收敛历史偏差时，建立独立任务并具备编译、测试、接口回归和必要的回退方案。

## 审核与验证清单

### 项目适配

1. 是否先遵循用户要求、项目显式规范和稳定既有实现？
2. 所谓“项目风格”是否有多处一致实现或明确配置支持，而非单个历史样本？
3. 是否避免为了套用默认规范扩大变更和迁移历史代码？

### 领域与依赖

1. 代码的领域归属和职责层是否明确？
2. 顶层包是否表达业务能力，而不是技术类型或临时页面名称？
3. Controller 是否只处理协议、校验、身份和响应转换？
4. 应用服务是否表达清晰用例和事务边界？
5. domain 是否避免依赖 Web、数据库、缓存、网络和具体基础设施？
6. Mapper、PO、第三方 DTO 和协议对象是否留在适配边界？
7. 跨领域调用是否通过公开应用接口、稳定端口或事件完成？

### 对象与共享

1. Request、Response、Command、Query、DTO、Entity、Value Object 和 PO 是否无歧义？
2. 转换职责是否位于对应边界，没有让外部对象穿透多层？
3. 共享代码是否确实稳定、通用且无单一领域所有者？
4. 是否避免为形式完整创建无价值接口、对象、目录和转换层？

### 工程边界

1. 日志级别、定位字段和敏感信息处理是否正确？
2. 配置是否有明确前缀、默认值、单位、环境覆盖方式和安全边界？
3. 异常是否在正确边界转换，没有吞异常或重复打印？
4. SQL、索引、分页、批量和超时是否按风险评估？
5. 事务是否位于用例边界，外部调用是否考虑幂等、重试和补偿？

### 验证

- 运行目标项目现有的格式化、静态检查、编译和测试；
- 根据风险验证数据库映射、接口契约、序列化、配置覆盖和外部调用；
- 涉及包移动时额外检查 XML、扫描路径、反射配置和框架扩展资源；
- 在结果中说明采用的项目既有约定、实际验证和未覆盖风险。
